# Relatório M13 — Hotfix 1.1.3: o laço de realimentação view→sinal→input

## 1. Resumo

A 1.1.2 ainda congelava (janela some, thread de UI a ~90–100%) porque
o diagnóstico anterior pegou só UM dos emissores dentro do
`update_view`. A causa real, reproduzida nesta máquina: um laço de
realimentação de duas mensagens — o setter observado por `#[watch]`
empurra um valor defasado do modelo para o ComboRow/SpinRow/Switch,
o `notify` re-enfileira um `Input` com o valor oposto, e o par
ping-pongava para sempre intercalado com `FrameReady`. Capturado ao
vivo: `SetGridColor(0) ↔ SetGridColor(1)` a ~250 updates/s —
exatamente o "valores alternando" previsto pela engenharia. Todos os
setters que emitem sinal saíram de `#[watch]` e agora rodam em
`post_view` atrás de comparação atual-vs-desejado com o handler de
sinal bloqueado — o mesmo padrão que `measure_ui.rs` já provou estável.

## 4. O que foi feito

### 4.1 O ComboRow da linha 621

`app.rs:621` é **`grid_color_row`** (ComboRow "Cor da grade"), não o
combo de calibração:

```rust
// ANTES
#[name = "grid_color_row"]
adw::ComboRow {
    set_title: strings::GRID_COLOR_LABEL,
    set_model: Some(&gtk::StringList::new(&strings::COLOR_NAMES)),
    #[watch]
    set_selected: model.config.overlays.grid.color.preset_index(),
    connect_selected_notify[sender] => move |row| {
        sender.input(Input::SetGridColor(row.selected()));
    },
},
```

```rust
// DEPOIS
#[name = "grid_color_row"]
adw::ComboRow {
    set_title: strings::GRID_COLOR_LABEL,
    set_model: Some(&gtk::StringList::new(&strings::COLOR_NAMES)),
    set_selected: model.config.overlays.grid.color.preset_index(),
    connect_selected_notify[sender] => move |row| {
        sender.input(Input::SetGridColor(row.selected()));
    } @grid_color_handler,
},
```

O sync contínuo migrou para `post_view` (ver §4.2). O handler de
`notify::selected` continua emitindo `SetGridColor` — mas agora a
escrita programática roda com o sinal bloqueado, então o `notify`
só chega de ação real do usuário.

### 4.2 O laço exato e a correção geral

**Mecânica do laço (reproduzida, não hipótese):**

1. O usuário (ou um teste dirigindo o widget) muda `selected` 0→1 →
   `Input::SetGridColor(1)` entra na fila — mas ainda **não** foi
   processado.
2. Um `FrameReady` (~10–30/s no teste; ~30/s ao vivo) roda
   `update_view` **antes** do Input: o `#[watch]` empurra o valor
   **antigo** do modelo (0) para o widget → `notify::selected` →
   `Input::SetGridColor(0)` enfileirado. Fila: `[1, 0]`.
3. Processa o 1: modelo=1 → `update_view` → `set_selected(1)` →
   widget 0→1 → emite `SetGridColor(1)`.
4. Processa o 0: modelo=0 → `update_view` → `set_selected(0)` →
   widget 1→0 → emite `SetGridColor(0)`.
5. Processa os ecos: mesmo com o guard `!=` no modelo (que evita
   regravar a config), o `update_view` roda **depois de cada Input**
   e re-escreve o widget para o valor oposto → novo eco. Ping-pong
   autossustentado — cada Input consome um e produz outro.

Log capturado na reprodução (o teste dirigiu `set_selected(1)` e o
laço explodiu para 50k+ updates em ~2 min, thread a 109% CPU):

```
[update #100] recent: ["SetGridColor(0)", "SetGridColor(1)", "SetGridColor(0)",
                       "SetGridColor(1)", "SetGridColor(0)", "SetGridColor(1)", ...]
... intercalado com "FrameReady"
```

O guard `!=` dentro do `update` **não bastava**: o Relm4 chama
`update_view` após qualquer `update`, mesmo sem mudança de modelo — e
era a re-escrita do widget que mantinha o ciclo.

**A correção** — todo setter que emite sinal saiu de `#[watch]` e
virou sync guardado em `post_view` (compara widget-vs-modelo; se
diferir, escreve com o handler bloqueado):

```rust
fn sync_selected(row: &adw::ComboRow, handler: &glib::SignalHandlerId, want: u32) {
    if row.selected() != want {
        row.block_signal(handler);
        row.set_selected(want);
        row.unblock_signal(handler);
    }
}
```

Com a escrita silenciada, o passo 3/4 acima não emite eco — a fila
drena e converge em ≤3 updates de cauda (medido no teste).

**`#[watch]`/`#[track]` corrigidos — lista completa:**

| Widget | Setter que emitia | Handler que re-enfileirava | Correção |
|---|---|---|---|
| `mode_explore_btn`/`mode_bench_btn` | `set_active` | `toggled` → `ModeToggled` | `sync_mode_buttons` — bloqueia OS DOIS (ativar um desativa o outro) |
| `grid_row` (SwitchRow, novo `#[name]`) | `set_active` | `notify::active` → `SetGridEnabled` | `sync_active` |
| `grid_spacing` (SpinRow) | `set_value` + `set_adjustment`/`set_digits` (imperativo) | `notify::value` → `SetGridSpacing` | `sync_value` + `sync_grid_unit` reconfigura só quando a assinatura (lo/hi/step/digits) difere, bloqueado |
| `grid_color_row` | `set_selected` | `notify::selected` → `SetGridColor` | `sync_selected` |

Setters `#[watch]` que **permanecem** (não emitem para Input —
nenhum handler conectado): `set_title`, `set_label`, `set_visible`,
`set_sensitive`, `set_revealed`, `set_show_sidebar`, `set_icon_name`,

(já proibidos pelo contrato da 1.1.2). Os toggles de modo foto/vídeo
(`mode_photo_btn`/`mode_video_btn`) nunca tiveram `#[watch]` em
`set_active` — sem caminho modelo→widget, sem risco.

Novo teste de contrato `no_watched_signal_setters` varre `app.rs` e
`measure_ui.rs` e **falha** se `set_selected`/`set_active`/`set_value`/
`set_adjustment` voltar a aparecer sob `#[watch]`/`#[track]`.

### 4.3 Calibração filtrada por dispositivo — mapeamento canônico

A suspeita da engenharia (índice da lista filtrada divergindo do
perfil) estava correta como *classe de risco*: `SelectCalibration`
usava `profiles_for(device).nth(index-1)` e `measure_ui::sync`
computava `position(name)+1` — duas expressões paralelas do mesmo
mapeamento. Agora é UM par canônico em `hiview-core`, pela identidade
do perfil (nome), nunca pela posição na lista completa:

```rust
// config.rs — única fonte do mapeamento index↔profile
pub fn active_profile_index(&self, device: &str) -> u32 { /* nome→índice+1, senão 0 */ }
pub fn profile_name_at(&self, device: &str, index: u32) -> Option<String> { /* índice→nome; 0/fora de faixa/u32::MAX → None */ }
```

`SelectCalibration`, `measure_ui::sync` e o teste de ida e volta
(`calibration_index_round_trips_per_device` — inclui perfis
intercalados de dois dispositivos e o `u32::MAX` transitório do GTK)
usam exatamente esse par.

### 4.4 Watchdog de diagnóstico

`InputLoopGuard` no modelo conta Inputs de seleção idênticos
(`selection_key` = Debug completo, valor incluso — cobre
`SetGrid*`, `SetCrosshair*`, `SetAdjust`, `ArmMeasureIndex`,
`SelectCalibration`, `ModeToggled`, `ShutterModeToggled`). Mais de
**10 idênticos em 1 s** → `tracing::warn!` uma vez por janela. No laço
reproduzido, cada valor alternado chegava a ~250/s — o guard dispara
em qualquer variante do bug (alternância ou repetição).

### 4.5 `FrameReady` pelo `update_view` inteiro — avaliação

`Input::FrameReady` não chama `update_view` diretamente — mas o Relm4
roda `update_view` após **qualquer** `update`, ou seja ~30×/s de
reavaliação do painel inteiro. Foi o `FrameReady` que *semeou* o laço
(o `update_view` dele empurrou o valor defasado enquanto o Input do
usuário esperava na fila). Após a correção, o custo por frame é ~12
comparações baratas — a decisão foi **manter**: um caminho que pule o
`update_view` exigiria tirar o viewport do ciclo do Relm4 (mudança de
arquitetura, CONVENTIONS §10 — proposta, não implementada). Se a
engenharia quiser, a alternativa é um canal lateral só para
`viewport.set_frame` + `tick_fps`, fora do componente.

## 5. Desvios da arquitetura ou das convenções

| O que diz o documento | O que foi feito | Por quê |
|---|---|---|
| Declarative-first (view!/`#[watch]`) | Setters com sinal migraram para `post_view` imperativo | É o único ponto com acesso a widget+modelo+`SignalHandlerId` para silenciar a reemissão — o laço vinha exatamente do declarativo |
| `FrameReady` pode atravessar `update_view` | Mantido | Pular exige mudança de arquitetura — proposto em §4.5 |
